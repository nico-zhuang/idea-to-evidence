# 意图发现引擎：从“要做 X”找到值得验证的 Y

这里的“识别意图”不是给一句话贴「产品/技术/闲聊」标签；要找的是**谁在什么情境下想取得什么进展，现用什么办法、为什么不够，什么观察能证明改变有价值**。此引擎只在想法研究触发时运行；明确执行任务、纯知识问答与“只讨论不研究”不做完整研究。

## 1. 先构造最小意图模型（内部，不默认输出表格）

按需辨认六项：原话提出的**方案/产物**、真正的**使用者与决策者**（跨团队或敏感数据场景再区分数据主体/授权者/结果接收者）、触发的**具体场景**、期望的**可观察结果**、现有**替代/绕路及其代价**、不可违背的**明示约束/非目标**。每项标【用户明说】【观察/资料】【推断】【未知】；引用他人口吻不等于用户同意；客户实际行为与用户对客户的猜测分开。不要将“提升效率”“更智能”当作可观察结果。

产品需求若依赖真实人群采用，优先找最近一次真实发生的事、当时如何应对、耗费的时间/风险/钱/协作成本；口头赞同、未来假设、演示热度不当作真实需求验证。**若用户明确禁止接触工单、会议记录或客户数据，不要索取最近一次真实客户案例**，也不让负责人转述可还原的个人内容；只能讨论公开流程定义或完全虚构情境，实际频率与效果仍标【未验证】，待另获授权再核实。个人探索或内部流程不强迫支付意愿、访谈数量或商业指标。

## 2. 只在实质不同的解释之间分叉

对“先做机器人/模型/App/平台”之类方案先写**原话解释**与**最多两个有根据的替代意图**，例如会议机器人可能为：①只要本人会议的行动项不遗漏；②必须合法获取全租户会中原始音频。检查两种解释是否改变 GitHub 查询词、可复用类别、关键权限或成功标准；若没有改变，不制造分叉，不为了显得深入而反驳用户。

用户已经明说的硬约束必须保留；可以提出更便宜的反事实选项供比较，但不能偷偷改目标。**来源材料提到的高风险能力（如全租户原始音频）不自动成为用户的诉求**：用户只说“全部会议内容”时，先按纪要/行动项等较弱解释判断，原声仅作为需要进一步确认的条件，不得写成【用户明说】。若后续答案纠正意图，立即撤回失效推断，更新检索词与候选比较，不沿用旧结论。不同利益相关者的要求发生冲突时，指出哪项冲突决定路线；不要静默选择更方便的一方。

## 3. 找“值得问的那一个问题”或直接推进

先从上下文、项目、公开文档回答可自行核实的事实；仅当**两种合理答案会使下一项研究、许可/权限路径或最终建议不同**时，提出一个短问题，并附当前倾向与为什么这个问题重要。不要问每个模板字段，也不要声称伪精确的 95% 置信度。用户不希望被追问时，明示暂定分支，分别做低风险、只读的研究；授权、付费、真实数据或不可逆操作仍须停下。用户只要求讨论而没授权研究则不检索。

决策敏感度按“错了会造成什么后果、两个答案是否改行动、能否低成本核实”比较，不强制打分。未定但不影响下一步的细节标【可延后】；缺少关键权限/目标冲突，不能宣称方案已可落地。

## 4. 别把方案搜对了，却把问题搜错了

GitHub 必查仍在**基本澄清之后、自建建议之前**。至少用两条语义线检索：用户提出的方案能力，以及其可能真正要完成的工作；若两者明显不同，应说明为什么额外搜另一条。现成平台功能、手工流程或“不做/推迟”同样是候选；仓库存在、README 宣称、Star 数都不是最终适配证据。按期望结果而不是仓库功能列表对比，许可证与真实运行证据照主文件核实。

把证据链压缩为：**用户原话/行为 → 工作假设 → 备选解释 → 搜索与实测 → 路径判断**。输出不必展示全部内部推演，但至少让用户看见一个经过检验的重构/分叉、哪条证据使建议发生变化，以及最小消疑动作。若研究否定了自己的初始判断，应明确更正，不硬凑支持材料。

## 5. 交付自检：检验是否真的带来决策增量

- 换一个更贴近真实工作的表述，会不会得出不同的 GitHub 查询与候选？若完全一样，可能只做了表面复述。
- 用户补充相反的现实条件时，推荐路线会不会随之转向？若不会，可能在套模板。
- 是否把用户明确的指定方案错误地当成“肯定没必要”，或把臆测的隐藏目标写成事实？两种都失败。
- 用户不答或拒绝提问时，是否还能在标明条件的前提下推进安全的只读研究，而非无限等待？
- 有没有把“需要一个仪表盘/模型/机器人”与“需要一个可做决定的名单/一次可靠交接/正式合规音频”区别开？
